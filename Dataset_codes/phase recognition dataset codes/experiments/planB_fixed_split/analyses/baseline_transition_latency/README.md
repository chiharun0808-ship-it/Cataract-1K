# 既存モデルの「切り替わりへの追いつき」の分析（2026-10-04）

案B の入力条件（サンプリング間隔・時間幅）を決めるための判断材料。
既存の予測ログを読むだけで、推論のやり直しも学習もしていない。既存のファイルは変更していない。

- 対象モデル: `result/epochs_35/sliding_window_checkpoints_0914_10_46/best_model.pth`
  （スライディングウィンドウ版。30枚・1/3秒間隔で、時間幅は約9.67秒）
- 対象データ: test 11症例の予測ログ（1秒ごと、平滑化なし、全4,387時点）
- 境目: 360か所（注釈の区間から求めた正確な切り替わり時刻）

## 結論
**今のモデルは、窓の時間幅が約9.67秒あるにもかかわらず、多くの切り替わりに約1秒以内で追いついている。**
窓の中身が新しいフェーズに入れ替わるのを待って判断しているわけではない。

- 予測が初めて新しいフェーズと一致するまでの時間（K=1）: 中央値 0.70秒 [95%CI 0.6, 0.7]。
  判定できた355か所のうち 97.2% が追いつき、93.2% が2秒以内。
- 3秒続けて当たるまで（K=3）でも、中央値 0.70秒。判定できた277か所のうち 90.3% が追いつく。
- 境目からの経過時間ごとの一致率: 0〜1秒は 76.9%、1〜2秒で 90.5% に戻る。
  参考線（窓の中で新しいフェーズの映像が占める割合）は1〜2秒で 16.7% なので、それよりずっと早い。
- 手術フェーズどうしの切り替わり（141か所）に限っても同じ傾向（K=1 で 97.2%、中央値 0.81秒）。

## 読むときの注意
- 記録は1秒ごとなので、1秒より細かい遅れは分からない。中央値0.7秒は「境目のあとの最初の記録で当たっている」ことを意味する。
- 予測の誤りの多くは、切り替わりの直後ではなく区間の途中で起きている（経過12秒以上でも一致率は約94%で、100%ではない）。
  LensPositioning などの誤り（非隣接の取り違え）は、遅れでは説明できない。
- 短い区間は判定できないことがある。新しい区間が3秒未満の126か所では、K=3 で83か所、K=5 で全126か所が「判定不能」。
  idle の区間は中央値 約2.6秒と短く、K を大きくするほど idle の判定不能が増える。
- この分析は「今の時間幅で遅れが問題になっているか」を見るもので、「時間幅を短くしたら良くなるか」は分からない（学習し直さないと分からない）。
- このモデルは学習と推論で入力の作り方が少し違う（mp4v の再エンコード、antialias）。その影響は含まれたまま。
- test 11症例は、これまでの分析でも何度も使っている（探索的な結果として扱う）。
- 旧モデル（クリップ単位）では、以前の分析で「切り替え直後2秒の一致率22%」だった（8/31、旧モデル fold_0 で test 11症例、経過時間の区切りが0〜2秒の別集計）。
  今回の数値と直接は比べられないが、学習方法を変えたことで遅れの性質が変わった可能性がある。

## 定義（2026-10-04 合意。詳細はスクリプト冒頭）
- 追いつくまでの時間: 区間の中で、K点（K = 1, 2, 3, 5秒）続けて予測が新しいフェーズと一致した最初の時点までの秒数。
- 結果の分類: 追いついた / 追いつかなかった（区間の中にK点以上の記録があるのに一致が続かなかった） / 判定不能（区間の中の記録がK点未満）。
- 補助の集計「手術フェーズどうしの切り替わり」: 注釈では全ての手術フェーズの間に idle が挟まっているため、
  「idle を挟んで、直前の手術フェーズと違うフェーズが始まる時点」と定義した。
  当初の書き方（idle を含まない境目）では0件になったため、意図に合わせて定義を明確にした。閾値や区切りは変えていない。
- フェーズごとの区間の長さの中央値は train 34症例の注釈から計算した（test の正解ラベルは使っていない）。
- 信頼区間: 症例を選び直すブートストラップ（2000回、乱数の固定値0）。
